# Prior art survey: composable SQL-as-text libraries

Ticket: `.scratch/plain_sql-spec/issues/01-prior-art-survey.md`.
Date of survey: 2026-09-26.
Sources: source code and official docs. Each claim cites its source. Remote sources are the `main` or `master` branch on the survey date. The elixir-dbvisor/sql clone is at `/Volumes/Code/personal/sql`, commit `f6097fff5b08efe9cd946a01cc2152c82d871cf7` (2026-09-20), version `0.6.0-dev`.

Terms follow `CONTEXT.md`: Fragment, Binding, Splicing, Dialect, Driver, Rendering. Library-specific names appear in backticks.

Each library section lists the six items of the ticket:

1. Fragment representation.
2. Splicing and Binding renumbering.

6. Helpers for recurring pains.

## sql-template-tag (JavaScript)

Source: <https://github.com/blakeembrey/sql-template-tag> (`src/index.ts`, `README.md`).

1. A Fragment is a `Sql` instance with two arrays: `strings` and `values`. The constructor checks `strings.length - 1 === values.length` (`src/index.ts`, class `Sql`). Placeholders do not exist in the stored text. Three getters render the text at read time: `sql` gives `?`, `text` gives `$1..$n`, `statement` gives `:1..:n` (`src/index.ts`, getters `sql`, `text`, `statement`).
2. Splicing happens in the constructor. When a value is a `Sql` instance, the constructor appends the child's first string to the current string, copies the child's values into the parent's `values`, and copies the child's remaining strings (`src/index.ts`, loop over `rawValues`). Renumbering is not needed. The numbers appear only when a getter renders the text.
3. There is no identifier helper. `raw(value)` creates a `Sql` with the text and no values. The README states "Do not accept user input to `raw`, this will create a SQL injection vulnerability" (`README.md`, section Raw).
4. `join(values, separator = ",")` creates one `Sql` with the values and the separators. `join([1, 2, 3]).sql` gives `"?,?,?"` (`README.md`, section Join). `join([])` throws `TypeError` (`src/index.ts`, function `join`). The Rendering is the same for every database. Only the placeholder style changes.
5. The README states: `This package "just works" with pg, mysql, sqlite and oracledb` (`README.md`, section Recipes). The library does not have a Dialect object. The portability promise covers the placeholder style only.
6. Helpers: `join` for lists and for `AND`-joined conditions, `raw` for text, `empty` (`raw("")`) for an optional clause, `bulk` for `VALUES (?,?),(?,?)` (`README.md`, sections Join, Raw, Empty, Bulk). The README shows the optional-clause idiom: `sql\`SELECT * FROM books ${hasIds ? sql\`WHERE ids IN (${join(ids)})\` : empty}\`` (`README.md`, section Usage).

## porsager/postgres (JavaScript)

Source: <https://github.com/porsager/postgres> (`src/types.js`, `README.md`).

1. A Fragment is a `Query` object created by the tagged template `sql\`...\``. It holds `strings` and `args` and is a lazy promise. The README states: "The lazy Promise implementation in Postgres.js is what allows it to distinguish Nested Fragments from the main outer query" (`README.md`, section Execute). Rendering happens in `stringify(q, string, value, parameters, types, options)` (`src/types.js`).
2. Splicing happens at Rendering time. `stringifyValue` calls `fragment(value, parameters, types, o)` when the value is a `Query`. `fragment` sets `q.fragment = true` and calls `stringify` with the same `parameters` array (`src/types.js`, functions `stringifyValue`, `fragment`). `handleValue` pushes each value into the shared `parameters` array and returns `'$' + types.push(...)`, so the placeholder number is the running count (`src/types.js`, function `handleValue`). The stored Fragment has no numbers. Numbers exist only in the rendered text.
3. `sql(string)` creates an `Identifier`. `escapeIdentifier` wraps the name in double quotes, doubles inner double quotes, and turns `.` into `"."` (`src/types.js`, class `Identifier`, function `escapeIdentifier`). The README example renders `select ${sql(column)} from ${sql(table)}` as `select "id" from "users"` (`README.md`, section Table names).
4. `sql([68, 75, 23])` creates a `Builder`. `Builder.build` inspects the SQL text before the placeholder with a regex per keyword and selects the `in` builder (`src/types.js`, class `Builder`, constant `builders`). The `in` builder renders `($1,$2,$3)`. For an empty list it renders `(null)` (`src/types.js`, `builders.in`). The README example is `where age in ${ sql([68, 75, 23]) }` (`README.md`, section Dynamic values and `where in`).
5. The library targets one database. The README title is "Fastest full-featured node & deno client" for PostgreSQL (`README.md`, header). The README does not make a cross-database promise.
6. Helpers: the empty Fragment `sql\`\`` for an optional clause (`README.md`, sections Partial queries, Dynamic filters), `sql(object, ...columns)` for `INSERT` and `UPDATE SET` column lists, `sql([...])` for `IN` and `VALUES`, `sql.unsafe(string)` for raw text (`README.md`, sections Dynamic inserts, Dynamic columns in updates, Unsafe raw string queries). The README gives no `AND`/`OR` join helper. Dynamic ordering uses a manual `flatMap` with `sql\`,\`` separators (`README.md`, section Dynamic ordering).

## slonik (JavaScript)

Source: <https://github.com/gajus/slonik> (`README.md`, `packages/sql-tag/src/`).

1. A Fragment is a frozen object `{ sql, values, type: FragmentToken }` created by `sql.fragment\`...\`` (`packages/sql-tag/src/factories/createSqlTag.ts`, `fragment`). The `sql` text contains placeholders in a private format. The README states: "Due to the way that Slonik internally represents SQL fragments, your query must not contain `$slonik_` literals" (`README.md`, section Fragments vs Queries). A query is the same object with a `parser` and `type: QueryToken`.
2. Splicing renumbers at Splicing time. `createFragmentSqlFragment(token, greatestParameterPosition)` rewrites each placeholder to `parameterPosition + greatestParameterPosition` with a regex (`packages/sql-tag/src/sqlFragmentFactories/createFragmentSqlFragment.ts`). It throws `UnexpectedStateError` when the greatest position exceeds `values.length` or when the least position is not 1. The README example nests two queries and gives `SELECT $1 FROM (SELECT $2 FROM bar)` with values `['baz', 'foo']` (`README.md`, section Nesting `sql`).
3. `sql.identifier(["bar", "baz"])` renders `"bar"."baz"`. Each name passes through `escapeIdentifier` and the names join with `.` (`packages/sql-tag/src/sqlFragmentFactories/createIdentifierSqlFragment.ts`). The README cites PostgreSQL delimited identifiers as the rule (`README.md`, section `sql.identifier`).
4. `sql.join(values, sql.fragment\`, \`)` renders one placeholder per value: `WHERE foo.b IN ($7, $8)` (`README.md`, section Protecting against unsafe value interpolation). An empty list throws `InvalidInputError("Value list must have at least 1 member.")` (`packages/sql-tag/src/sqlFragmentFactories/createListSqlFragment.ts`). The README recommends `sql.array` instead: `WHERE id = ANY(${sql.array([1, 2, 3], "int4")})` renders `$1::"int4"[]`, gives a stable query text, and accepts an empty array (`README.md`, section `sql.array` vs `sql.join`).
5. The library targets one database. The README describes Slonik as "A battle-tested Node.js PostgreSQL client" (`README.md`, header). The README does not make a cross-database promise.
6. Helpers: `sql.and` and `sql.or` filter out `false`, `null`, `undefined` members. An empty `sql.and` renders `TRUE`. An empty `sql.or` renders `FALSE` (`README.md`, sections `sql.and`, `sql.or`; `createSqlTag.ts`, `and`, `or`). `sql.list` joins with `, `. `sql.join` takes a custom glue. `sql.unsafe` and `sql.literalValue` inject text (`README.md`, section Query building).

## sqlbind and sqlbind-t (Python)

Source: <https://github.com/baverman/sqlbind> (`README.md`, `sqlbind/__init__.py`) and <https://github.com/baverman/sqlbind-t> (`README.md`). The sqlbind README states: "sqlbind is deprecated in favor of sqlbind-t" and lists the reason: "Which dialect and mark style to use is decided only on final step when query needs to be rendered to raw SQL and parameters" (`sqlbind/README.md`, section DEPRECATED).

1. sqlbind: a Fragment is an `Expr`, a subclass of `str` with the placeholders already rendered. The values accumulate in a `QueryParams` object `q`. `q` is a `list` or a `dict` and the caller selects the marker style when it creates `q` (`sqlbind/__init__.py`, classes `Expr`, `QueryParams`, `QMarkQueryParams`, `NamedQueryParams`, `DollarQueryParams`). sqlbind-t: a Fragment is a Python t-string `Template` or a thin `SQL` wrapper. The README states: "sqlbind-t doesn't parse SQL in t-strings. It only concatenates stuff and extracts interpolations as execution parameters" (`sqlbind-t/README.md`, section Quick start).
2. sqlbind: Splicing is string concatenation. The values join `q` in Binding order, not in text order. The README shows the failure: two filters bound in one order and spliced in the other give `['2023-01-01', 1]` against `enabled = ? AND registered > ?`, and states "parameter ordering mismatches placeholders" (`sqlbind/README.md`, section Outro). sqlbind-t: nested templates render at `render` time, so the values follow the text order. `UNDEFINED` values are processed per template: an inner template with `UNDEFINED` renders as an empty string and the outer template stays (`sqlbind-t/README.md`, section Conditional markers).
3. `E.table.field` and `E('"weird table"."weird column"')` emit the text as-is. The README lists them under "Trusted SQL fragments and identifiers" and states "Use them only with trusted strings (not user input)" (`sqlbind-t/README.md`). Neither library quotes identifiers.
4. `BaseDialect.IN` binds the whole list as one value: `field IN ?` with `[[10, 20]]` (`sqlbind/__init__.py`, class `BaseDialect`). `SQLiteDialect.IN` expands to `field IN (?,?)` and, above 10 values, inlines escaped literals to avoid the parameter limit (`sqlbind/__init__.py`, class `SQLiteDialect`, docstring of `QueryParams.IN`). An empty list renders `dialect.FALSE`, which is `FALSE` or `0` for SQLite (`sqlbind/__init__.py`, `QueryParams.IN`). sqlbind-t: "PostgreSQL dialect renders `IN` as `= ANY(array_param)`" and "SQLite dialect expands `IN` lists and falls back to literal expansion for long lists" (`sqlbind-t/README.md`, section Dialects).
5. Both READMEs state: "Supports all DBAPI parameter styles" (`sqlbind/README.md`, `sqlbind-t/README.md`, header). sqlbind-t states: "The default `sqlbind_t.dialect.Dialect` is generic; specialized dialects adjust how some operations render (notably `IN`)" (`sqlbind-t/README.md`, section Dialects). The SQL text is not rewritten.
6. Helpers: `WHERE`, `AND_`, `OR_`, `WITH`, `SET`, `GROUP_BY`, `ORDER_BY`, `LIMIT`, `OFFSET`. Each omits empty parts and renders an empty string when all parts are empty (`sqlbind/__init__.py`, functions `prefix_join`, `WHERE`, `AND_`; `sqlbind-t/README.md`, section WHERE prepender). Conditional markers `not_none`, `truthy`, `cond` turn a value into `UNDEFINED` and empty the expression (`sqlbind/__init__.py`, classes `NotNone`, `Truthy`, `cond`). sqlbind-t adds `required`, which empties the parent template when the nested template is empty (`sqlbind-t/README.md`, section Conditional markers).

## sqlx `QueryBuilder` (Rust)

Source: <https://github.com/launchbadge/sqlx> (`sqlx-core/src/query_builder.rs`, `README.md`, `FAQ.md`).

1. A `QueryBuilder<DB>` holds `query: Arc<String>` and `arguments: Option<DB::Arguments>` (`query_builder.rs`, struct `QueryBuilder`). There is no Fragment value type. `push(sql)` appends text. `push_bind(value)` adds the value to `arguments` and calls `arguments.format_placeholder(query)`, which writes `?` or `$N` for the database type (`query_builder.rs`, `push_bind`; doc comment: "Push a bind argument placeholder (`?` or `$N` for Postgres)").
2. Splicing does not exist. The builder appends in call order. `with_arguments(init, arguments)` accepts existing text and arguments and "does *not* check if `arguments` is valid for the given SQL" (`query_builder.rs`, `with_arguments`). The doc comment on `build` states: "It is your responsibility to ensure that you produce a syntactically correct query here, this API has no way to check it for you" (`query_builder.rs`, `build`).
3. There is no identifier helper. `push` carries a warning: "This method does *not* perform sanitization" (`query_builder.rs`, `push`).
4. `separated(", ")` returns a `Separated` that pushes the separator before each `push_bind`. The doc example builds `in (?, ?)` and states: "an empty vector would cause a sql syntax error" (`query_builder.rs`, `separated`). The FAQ states: "In the future SQLx will support binding arrays as a comma-separated list for every database, but unfortunately there's no general solution for that currently in SQLx itself" and gives the Postgres form `WHERE id = ANY($1)` (`FAQ.md`, section How can I do a `SELECT ... WHERE foo IN (...)` query?). The FAQ also states: "`!= ANY($1)` is **not equivalent** to `NOT IN (...)`" and gives `!= ALL($1)` as the equivalent.
5. The README states: "**Database Agnostic**. Support for PostgreSQL, MySQL, MariaDB, SQLite" and "Since SQLx never has to parse the SQL string itself, any syntax that the development DB accepts can be used" (`README.md`, header and section SQLx is not an ORM!). The quickstart tells the developer to write `$1` for Postgres and `?` for MySQL (`README.md`, section Quickstart). The developer owns the placeholder style in hand-written SQL. Only `QueryBuilder::push_bind` selects it.
6. Helpers: `separated`, `push_values` for `VALUES (..),(..)`, `push_tuples` for `IN ((..),(..))`, `reset` (`query_builder.rs`). The doc comments state that an empty `tuples` "will likely produce a syntactically invalid query" (`query_builder.rs`, `push_values`, `push_tuples`).

## sea-query (Rust, contrast: a DSL)

Source: <https://github.com/SeaQL/sea-query> (`README.md`).

1. A query is an abstract syntax tree. The README states: "You can construct expressions, queries and schema as abstract syntax trees using an ergonomic API" (`README.md`, section SeaQuery). `build(PostgresQueryBuilder)` returns `(String, Values)`. `to_string` inlines the values for debugging (`README.md`, section Statement Builders).
2. Splicing is AST composition. `Expr::cust_with_values(r#""size_w" = $2 * $1"#, [3, 2])` uses a local numbering. The README states: "custom expressions only need to define local parameter sequence. its global sequence will be re-written" (`README.md`, section Parameter bindings). The example renders `"id" = $1 AND ("size_w" = $2 * $3) AND "size_h" > $4`.
3. Identifiers are `Iden` values. The backend quotes them: `"glyph"` for Postgres and SQLite, `` `glyph` `` for MySQL (`README.md`, sections Iden, Query Select).
4. `Expr::col("id").is_in([3, 4, 5])` renders `"id" IN ($4, $5, $6)` with one placeholder per value (`README.md`, section Parameter bindings). `raw_query!` expands `{..d}` to the same form (`README.md`, section Improved raw SQL ergonomics). The README does not show the Rendering of an empty list.
5. The README states: "With SeaQuery, you can target multiple database backends while maintaining a single source of query logic" and shows one `on_conflict` AST rendered as `ON DUPLICATE KEY UPDATE` for MySQL and `ON CONFLICT ... DO UPDATE SET` for Postgres and SQLite (`README.md`, section Cross database support). This is SQL rewriting by the backend. The README also states: "We support MySQL, Postgres and SQLite behind a common interface that aligns their behaviour where appropriate" (`README.md`, section SeaQuery).
6. Helpers: `apply_if(option, closure)` for an optional condition, `Cond::all()` and `Cond::any()` with `any!` and `all!` macros. The README states: "There is no superfluous parentheses `((((` cluttering the query, because SeaQuery respects operator precedence when injecting them" (`README.md`, section Dynamic query).

## Ecto `fragment/1` (Elixir)

Source: <https://hexdocs.pm/ecto/Ecto.Query.API.html>, <https://hexdocs.pm/ecto/Ecto.Query.html#dynamic/2>, <https://github.com/elixir-ecto/ecto_sql> (`lib/ecto/adapters/postgres/connection.ex`, `lib/ecto/adapters/myxql/connection.ex`).

1. A fragment is a query expression node `{:fragment, _, parts}`. The parts are `{:raw, text}` and `{:expr, expr}`. The docs state: "Every occurrence of the `?` character will be interpreted as a place for parameters, which must be given as additional arguments to `fragment`" (Ecto.Query.API, `fragment/1`). The adapter renders each `{:expr, expr}` with `maybe_paren`/`op_to_binary` (`postgres/connection.ex`, `myxql/connection.ex`, `fragment_expr/3`).
2. A fragment is one expression inside an Ecto query AST. Interpolated values `^value` become `{:^, [], [ix]}`. Postgres renders `$#{ix + 1}` and MySQL renders `?` (`postgres/connection.ex`, `myxql/connection.ex`, `expr({:^, [], [ix]}, ...)`). Ecto assigns the index when it builds the query, so a fragment inside a `dynamic` renumbers when the `dynamic` is interpolated into a query. `splice(^list)` expands one argument into one `?` per element: `fragment("? in (?)", p.id, splice(^[1, 2, 3]))` becomes `fragment("? in (?,?,?)", p.id, ^1, ^2, ^3)` (Ecto.Query.API, `splice/1`).
3. `identifier(^name)` renders `quote_name(literal)`. Postgres wraps the name in double quotes and raises `bad literal/field/index/table name ... (" is not permitted)` when the name contains a double quote. MySQL wraps the name in backticks and raises for a backtick (`postgres/connection.ex`, `myxql/connection.ex`, `expr({:identifier, _, [literal]}, ...)`, `quote_name/1`). The docs state: "Ecto will make these values directly part of the query, handling quoting and escaping where necessary" and "each different value ... will emit a different query, which will be independently prepared and cached" (Ecto.Query.API, `fragment/1`, Identifiers and Constants).
4. `x in ^list` with an interpolated list renders `= ANY($n)` on Postgres (`postgres/connection.ex`, `expr({:in, _, [left, {:^, _, [ix, _]}]}, ...)`). MySQL renders `IN (?,?,?)` with one `?` per element, taken from the list `length` (`myxql/connection.ex`, `expr({:in, _, [left, {:^, _, [_, length]}]}, ...)`). Both adapters render `false` for an empty list (`expr({:in, _, [_left, []]}, ...)` and the MySQL `{:^, _, [_, 0]}` clause).
5. The docs state: "It is very important to keep in mind that Ecto is unable to do any type casting when fragments are used" (Ecto.Query.API, `fragment/1`). Adapters raise `Ecto.QueryError` for constructs they do not support, for example MySQL: "ilike is not supported by MySQL" and "Array type is not supported by MySQL" (`myxql/connection.ex`). Ecto does not promise that a fragment text runs on every adapter.
6. Helpers: `dynamic/2` builds a condition "bit by bit" with `and`/`or` and interpolates it at the root of a `where` (Ecto.Query, `dynamic/2`). `where` composes with `AND`; `or_where` with `OR` (Ecto.Query, `where/3`, `or_where/3`). `splice/1`, `identifier/1`, `constant/1`, `type/2` extend `fragment/1` (Ecto.Query.API).

## ayesql (Elixir)

Source: <https://github.com/alexdesousa/ayesql> (`README.md`, `lib/ayesql/ast/context.ex`, `lib/ayesql/runner.ex`).

1. A query is SQL text in a `.sql` file with a `-- name:` comment. Parameters are `:name` (mandatory) and `:_name` (optional). Another query is referenced as `:query_name` (`README.md`, section Parameters). At runtime an `AyeSQL.AST.Context` accumulates `statement` (a list of binaries), `arguments`, and `index` (`lib/ayesql/ast/context.ex`, `defstruct`). `to_query` joins the statement, normalises whitespace, and returns `%AyeSQL.Query{statement, arguments}` (`context.ex`, `to_query/1`, `join_statement/1`).
2. `put_variable` writes `"$#{index}"`, appends the argument, and increments `index` (`context.ex`, `put_statement/2`, `put_variable/2`). `merge_query(context, query)` splices a composed query: it appends the query statement and adds `length(query.arguments)` to the index (`context.ex`, `merge_query/2`). The composed query is rendered with its own numbering before the merge. The source does not show a renumbering step for the spliced text; the offset is applied to the parent index only.
3. There is no identifier helper. The README does not describe identifier binding.
4. `{:in, list}` calls `put_variables`, which renders one `$N` per value and joins them with `,` (`context.ex`, `put_variables/2`; `README.md`, section IN Statement).
5. The README states the library aims to "Work out-of-the-box with PostgreSQL using Ecto or Postgrex" and "Work out-of-the-box with DuckDB using Duckdbex" (`README.md`, section Overview). The placeholder is always `$N` (`context.ex`, `put_statement/2`). A runner implements `run(query, options)` (`lib/ayesql/runner.ex`, `@callback run/2`).
6. Helpers: optional fragments `:_order_by` that render nothing when the parameter is absent, composition by name, `{:inner, keyword, separator}` for lists of sub-fragments, and a `<missing key>` marker with a `:not_found` error for a missing mandatory parameter (`README.md`, sections Optional fragments, Subqueries and subfragments; `context.ex`, `not_found/2`).

## elixir-dbvisor/sql (Elixir)

Source: local clone `/Volumes/Code/personal/sql`, commit `f6097fff`. Files cited with paths relative to the clone.

1. A query is a `%SQL{}` struct with `tokens`, `params`, `vars`, `string`, `adapter`, and pool fields (`lib/sql.ex`, `defstruct`). The `~SQL` sigil lexes and parses the text with a full SQL grammar (`lib/sql.ex`, `build/4`; `lib/lexer.ex`; `lib/parser.ex`; `lib/bnf.ex`). A Binding is `{{expr}}`. The lexer parses the content of `{{...}}` as Elixir code with `Code.string_to_quoted!` and emits a `:binding` token (`lib/lexer.ex`, function `double_brace`, line 749-750). `to_sql/1` returns `{sql.string, sql.params}` (`lib/sql.ex`, `to_sql/1`).
2. Splicing uses the pipe: `~SQL[from users] |> ~SQL[where email = {{email}}] |> ~SQL"select id, email"` (`README.md`, section Examples). For static sigils the macro joins the texts with one space at compile time (`lib/sql.ex`, `build/2`, clause `[value, ?\s, acc]`). For a piped runtime value the macro concatenates token lists with `collect/1` and re-parses (`lib/sql.ex`, `build/4` dynamic clause, `collect/3`). The parser reorders clauses, so `from ... where ... select` renders as `select ... from ... where` (`README.md`, section Examples). The adapter renders placeholders while it walks the tokens from the end; the Postgres adapter reads a counter from the process dictionary and decrements it per Binding (`lib/adapters/postgres.ex`, `to_iodata({:binding, ...})`; `lib/token.ex`, `to_iodata/2`, `Process.put(:sql_binding, binding)`). The counter starts at `context.binding`, which the lexer computes for one sigil text (`lib/lexer.ex`, `@context`, line 750). The Postgres test for a piped query with a Binding in the left segment asserts `$0::int4 ... = $1` (`test/adapters/postgres_test.exs`, lines 245 and 253). `$0` is not a valid PostgreSQL placeholder. This survey reads the asserted text as the current behaviour of the clone, not as a design intent.
3. Quoted identifiers pass through the lexer as `:double_quote` and `:backtick` tokens and render back with the same delimiters (`lib/lexer.ex`, lines 253-259, 698; `lib/token.ex`, `__to_iodata__` clauses for `:double_quote`, `:backtick`). There is no identifier Binding helper. `{{expr}}` is always a value Binding.
4. The Postgres adapter rewrites `left in {{list}}` to `left = ANY($n)` and `left not in {{list}}` to `left != ANY($n)` (`lib/adapters/postgres.ex`, `to_iodata({:in, ...})` clauses). The ANSI, MySQL, and TDS adapters keep `in ?` and bind the whole list as one value (`test/adapters/ansi_test.exs`, line 209-213: `select ? in ?`; `test/adapters/mysql_test.exs`, `test/adapters/tds_test.exs`, same lines). When the Binding carries a cast, the rewrite does not apply: `{{1}}::int4 in {{[1, 2]}}::int4[]` renders `$1::int4 in $2::int4[]` (`test/adapters/postgres_test.exs`, lines 271-277).
5. The README does not contain a portability statement. It lists one adapter per pool (`README.md`, section Pool configuration). The CHANGELOG lists ANSI, MySQL, PostgreSQL, and TDS adapters (`CHANGELOG.md`, lines 48-52). Placeholder styles: `?` for ANSI and MySQL, `$N` for Postgres, `@N` for TDS (`lib/adapters/ansi.ex`, `lib/adapters/mysql.ex`, `lib/adapters/postgres.ex`, `lib/adapters/tds.ex`).
6. Helpers: none for an optional `WHERE`, for joining conditions, or for an empty list. The tests use `~SQL""` as an empty default and pipe onto it (`test/adapters/postgres_test.exs`, `def from(sql \\ ~SQL"")`). The README lists "Composable Queries: No need to remember `SELECT` vs `FROM` order" as the composition feature (`README.md`, section Highlights).

## sqlglot (Python, contrast: full transpiling)

Source: <https://github.com/tobymao/sqlglot> (`README.md`).

1. A query is an AST. `parse_one(sql, dialect=...)` parses. `expression.sql(dialect=...)` renders (`README.md`, sections FAQ, AST Introspection).
2. Splicing is AST modification: `parse_one("SELECT x FROM y").from_("z")`, `condition("x=1").and_("y=1")`, and `transform` over nodes (`README.md`, section Build and Modify SQL). Bindings are not a feature of the README examples; the library produces SQL text.
3. `identify=True` quotes all identifiers with the target dialect's delimiter. The Spark example renders backticks (`README.md`, section Formatting and Transpiling).
4. Not applicable. The README does not describe `IN` list Binding.
5. The README states: "SQLGlot is a transpiler, not a validator. A query that parses successfully may still fail at execution time" and "Transpilation is a hard problem, so SQLGlot solves it incrementally. Some dialect pairs may lack support for certain inputs" (`README.md`, sections FAQ, Unsupported Errors). Unsupported constructs give a warning and a best-effort translation by default; `unsupported_level=ErrorLevel.RAISE` raises `UnsupportedError` (`README.md`, section Unsupported Errors). The README lists over 30 dialects with Official, Community, and Plugin support levels (`README.md`, section Supported Dialects).
6. Not applicable. sqlglot changes what the SQL says. PlainSQL's charter excludes this (`.scratch/plain_sql-spec/map.md`, section Out of scope).

## Findings relevant to tickets 02 and 04

1. Two Splicing designs exist for text-plus-values Fragments. Design A stores no placeholder numbers and assigns them at Rendering (sql-template-tag `Sql.text` getter; porsager/postgres `handleValue`; sqlbind-t `render`). Design B stores private numbered placeholders and renumbers by offset at Splicing (slonik `createFragmentSqlFragment`, sea-query `cust_with_values`). Design A needs no rewrite pass and no reserved marker in the SQL text. Design B needs a reserved marker (`$slonik_`) and a validation step.
2. Every text-based library that supports positional Drivers joins Bindings in text order at Splicing or Rendering. sqlbind (deprecated) is the one library that accumulated values in Binding order, and its README documents the resulting placeholder mismatch. sqlbind-t moved to render-time ordering and names this as the reason for the rewrite.
3. An empty Fragment is a first-class value in the libraries that support optional clauses: `empty` in sql-template-tag, `` sql`` `` in porsager/postgres, `EMPTY`/`UNDEFINED` in sqlbind, `~SQL""` in elixir-dbvisor/sql tests. Splicing an empty Fragment adds no text and no Bindings.
4. `AND`/`OR` join helpers define the empty case as a boolean literal: slonik `sql.and([])` renders `TRUE` and `sql.or([])` renders `FALSE`. sqlbind `WHERE()`, `AND_()`, `OR_()` render an empty string and omit the keyword. Ecto and the two Postgres clients render `false` or `(null)` for an empty `IN` list. A decision for ticket 02 has three precedents: boolean literal, omitted clause, or raise (slonik `sql.join([])`, sql-template-tag `join([])`).
5. `IN` list Rendering is the one place where surveyed libraries change the SQL text per Dialect: Postgres `x = ANY($1)` with one array Binding (Ecto, sqlbind-t, elixir-dbvisor/sql, sqlx FAQ, slonik `sql.array`) versus `x IN (?, ?, ?)` with one Binding per element (Ecto MySQL, sqlbind SQLite, sea-query, ayesql, sqlx `separated`). The sqlx FAQ states that `!= ANY($1)` is not equivalent to `NOT IN (...)`; the equivalent is `!= ALL($1)`. The elixir-dbvisor/sql Postgres adapter renders `not in {{list}}` as `!= ANY($n)`.
6. SQLite has a bind-parameter limit. sqlbind inlines escaped literals above 10 values; sqlx documents 32766 (999 before 3.32.0) and Postgres/MySQL 65535, MSSQL 2100. A per-element `IN` expansion under SQLite has a ceiling; `= ANY(array)` under Postgres does not.
7. Identifier Binding is quoting, not parameterisation, in every library that offers it: porsager/postgres `escapeIdentifier`, slonik `escapeIdentifier`, Ecto `quote_name`, sea-query `Iden`. Postgres and SQLite use `"`, MySQL uses `` ` ``. Ecto raises when the name contains the delimiter; porsager/postgres doubles it. Ecto documents that each identifier value produces a distinct prepared statement.
8. No text-based library promises that one SQL text runs on every database. sql-template-tag and sqlbind promise placeholder-style portability only. sqlx states it never parses the SQL. Ecto states it cannot type-cast inside fragments and its adapters raise on unsupported constructs. sea-query and sqlglot are the contrast: both rewrite SQL per backend, and sqlglot states this is "a hard problem" solved "incrementally" with best-effort output. This supports the charter's closed divergence list (placeholder style, identifier quoting, `IN` expansion) and the exclusion of transpiling.
9. Libraries that rewrite SQL per Dialect at Rendering (Ecto `in`, elixir-dbvisor/sql Postgres `in`) need grammar knowledge of the surrounding text. The elixir-dbvisor/sql rewrite fails to apply when a cast follows the Binding (`in {{list}}::int4[]` renders `in $2::int4[]`). porsager/postgres selects the `in` builder by regex on the preceding text. A helper that takes the list explicitly (slonik `sql.array`, sqlbind `q.IN(field, values)`, Ecto `splice`) needs no grammar knowledge.
10. Composition across full-parse libraries reorders clauses (elixir-dbvisor/sql renders `from |> where |> select` as `select ... from ... where`). This requires the full SQL grammar and is the feature PlainSQL's charter excludes ("No SQL grammar parsing"). The other text-based libraries treat Splicing as text-in-position with no reordering.
